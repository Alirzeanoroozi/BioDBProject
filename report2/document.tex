	\section*{Recap of Report 1: Objectives and Key Findings}
	
	
	This part presents a comprehensive summary of the first phase of the final project, which focused on the design and implementation of a reproducible biological data acquisition pipeline for the study of schwannoma. The primary objective of the first report was to collect, integrate, and organize heterogeneous biological data sources at the genomic, transcriptomic, and proteomic levels in a manner suitable for downstream database design, querying, and visualization.
	
	\subsection*{Overall Objectives and Conceptual Framework}
	
	The first report adopted a disease-centered strategy rather than relying on a manually curated gene list. Schwannoma was selected as the target phenotype, and all subsequent data collection steps were driven by this disease context. The overarching goals were to identify schwannoma-associated genes, expand this gene set using biological interaction networks, retrieve genetic variation data at scale, incorporate transcript-level genomic structure, map genes to proteins, and identify relevant gene expression datasets. A key design principle was reproducibility, ensuring that every step could be rerun using public databases and stable identifiers.
	
	\subsection*{Phenotype-Driven Gene Identification}
	
	The pipeline began with the identification of genes associated with schwannoma using Ensembl BioMart. The Human genes dataset based on the GRCh38.p14 assembly was queried using the phenotype filter \textit{schwannoma}. This approach avoided subjective gene selection and ensured that all retrieved genes were explicitly linked to the disease phenotype through Ensembl annotations. Core gene-level attributes were extracted, including Ensembl Gene Stable ID, gene name, chromosome or scaffold, and genomic start and end positions. Ensembl Gene Stable IDs were used as primary identifiers throughout the project, enabling reliable integration across multiple external data sources.
	
	\subsection*{Network-Based Gene Expansion}
	
	To capture broader biological context beyond directly phenotype-associated genes, the initial gene list was expanded using the STRING protein–protein interaction database. The Ensembl-derived gene list was submitted to STRING under the organism constraint \textit{Homo sapiens}. A full STRING network was constructed with all evidence channels enabled, including curated databases, experimental evidence, text mining, co-expression, neighborhood, gene fusion, and co-occurrence. A minimum interaction confidence score of 0.400 was applied, and expansion was restricted to the first interaction shell with a maximum of 100 interactors. This process resulted in a biologically coherent interaction network consisting of 72 nodes. The expanded gene set was treated as the definitive gene universe for all subsequent data collection steps.
	
	\subsection*{Genetic Variant Retrieval}
	
	Following gene set finalization, genetic variation data associated with the expanded gene universe were retrieved using Ensembl BioMart. All genes were represented using Ensembl Gene Stable IDs to ensure compatibility with Ensembl variation resources. Variant data were queried from the \texttt{hsapiens\_snp} dataset and restricted to variants sourced from dbSNP. For each variant, attributes such as gene identifier, gene name, dbSNP reference ID, chromosome, genomic coordinates, allelic information, and UCSC identifiers were collected. These attributes were selected to support both biological interpretation and relational database design.
	
	\subsection*{Automated Large-Scale Variant Acquisition}
	
	Due to BioMart browser limitations, including session timeouts and incomplete query results, an automated Python-based solution was developed. The workflow divided the gene list into small chunks, generated XML-based BioMart queries, and submitted them programmatically using HTTP POST requests. To improve robustness, multiple Ensembl BioMart mirrors were used with retry logic and logging. Each chunk was processed independently, written to a separate output file, and later merged into a single consolidated variant table with exactly one header preserved. Genes producing no variant records were explicitly tracked. Through extensive testing, a chunk size of four genes per query was identified as the most stable configuration. Although this approach required approximately 20 hours to complete, it successfully produced a complete and reproducible large-scale variant dataset.
	
	\subsection*{Transcript-Level Genomic Structure}
	
	To enable exon-aware and transcript-centric analyses, transcript-level annotations were retrieved using the UCSC Table Browser. Queries were performed on the hg38 genome assembly using the NCBI RefSeq track and the \texttt{ncbiRefSeq} table. For each gene, all available transcripts were retrieved rather than selecting a single canonical transcript. Extracted attributes included transcript accession identifiers, chromosome, strand, transcript start and end positions, exon counts, exon start positions, exon end positions, and gene symbols. This strategy preserved alternative splicing information and avoided biases introduced by transcript selection.
	
	\subsection*{Gene–Protein Mapping}
	
	To link genomic information to protein-level data, gene identifiers were mapped to UniProt entries using the UniProt ID Mapping service. This mapping enabled integration of protein-centric attributes such as protein names, functional annotations, and cross-references to structural databases. The resulting gene–protein associations provide a critical bridge between genetic variation, transcript structure, and protein function within the database schema.
	
	\subsection*{Expression Dataset Identification}
	
	The final step of the first report involved identifying a relevant gene expression dataset for schwannoma. An advanced search of the Gene Expression Omnibus (GEO) was conducted using the keyword \textit{schwannoma}, restricted to \textit{Homo sapiens}, and limited to studies published from 2005 onward. Based on relevance and data quality, the dataset GSE39645 was selected. Although differential expression analysis was not performed at this stage, the dataset selection established the foundation for later GEO2R-based analysis and expression-level integration.
	
	\subsection*{Protein Structure and Domain Resources (TED, CATH, and AlphaFoldDB).}
	In Part~6 of the report, structural and domain-level information for proteins associated with the schwannoma gene set was incorporated using three complementary resources: TED, CATH, and AlphaFoldDB. The TED database was used to identify experimentally determined protein domain boundaries and structural classifications derived from known structures. CATH provided a hierarchical domain classification system, enabling the assignment of protein domains into Class, Architecture, Topology, and Homologous superfamily levels, which supports functional inference and evolutionary analysis. Since many proteins lack experimentally resolved structures, AlphaFoldDB was employed to supplement structural coverage by providing high-confidence predicted three-dimensional protein models generated using deep learning. Together, these resources enabled comprehensive structural annotation of proteins, allowing the project to bridge genomic and proteomic data with structural biology and to support future structure-aware analyses and visualization within the database framework.
	
	\subsection*{Entity--Relationship Diagram and Database Constraints.}
	In Part~7, the report describes the construction of an Entity--Relationship Diagram (ERD) to formally represent the structure of the biological database and to define the relationships among genes, variants, transcripts, proteins, and expression data. The ERD was designed to reflect the logical organization of the data acquisition pipeline and to ensure that all entities are connected through biologically meaningful relationships. Primary keys were defined for each entity to guarantee uniqueness, while foreign keys were introduced to enforce referential integrity across tables. Additional constraints, such as one-to-many and many-to-many relationships, were explicitly modeled to capture the multiplicity inherent in biological data, for example between genes and transcripts or genes and variants. These constraints play a critical role in preventing data inconsistency, supporting efficient querying, and ensuring that the physical database implementation accurately reflects the conceptual design established earlier in the project.
	
	
	\subsection*{Overall Outcomes}
	
	In conclusion, the first report delivered a complete, end-to-end data acquisition and integration pipeline for schwannoma research. It produced a phenotype-driven and network-expanded gene set, a large-scale and reproducibly retrieved variant dataset, transcript-level genomic structure from UCSC, gene–protein mappings from UniProt, and a curated expression dataset from GEO. These outputs form the biological and technical foundation for the physical database design, testing, and visualization tasks addressed in the second phase of the project.

	\section*{Database Constraints in the Physical Design (5 pts)}
	
	The physical schema enforces data quality and relational consistency through a combination of \textbf{key constraints}, \textbf{referential integrity constraints}, and \textbf{domain-level constraints}. At the entity level, each table has a well-defined primary key: for example, \texttt{Genes} uses an Ensembl stable identifier as the primary key, while \texttt{Variants} and \texttt{STRING\_Interactions} use composite primary keys to guarantee uniqueness for relationship-like records:contentReference[oaicite:1]{index=1}. We also apply \textbf{unique constraints} where needed (e.g., gene symbols) to support stable joins when an external source primarily uses gene symbols rather than Ensembl IDs:contentReference[oaicite:2]{index=2}.
	
	For \textbf{foreign key constraints}, child tables reference parent identifiers to prevent orphan records and preserve the conceptual relationships defined in the ERD. Examples include linking variants and proteins back to \texttt{Genes}, linking structural domains back to \texttt{Proteins}, and linking expression results back to genes (gene symbol):contentReference[oaicite:3]{index=3}:contentReference[oaicite:4]{index=4}. We also specify \textbf{referential actions} to control how updates/deletes propagate: for many dependent tables we use \texttt{ON DELETE CASCADE} / \texttt{ON UPDATE CASCADE} to keep the database consistent when a parent identifier changes, while for transcript records we use a more conservative strategy (\texttt{SET NULL}) to preserve transcript-level data even if the gene mapping becomes unavailable:contentReference[oaicite:5]{index=5}. Finally, we enforce basic domain constraints such as \texttt{NOT NULL} on key columns, appropriate numeric types for genomic coordinates, and indexing of foreign key columns (for join performance), all of which are reflected in the DDL and in the Workbench constraint panels (Figures~\ref{fig:part3_PrimaryKey}--\ref{fig:part3_ForeignKey_sql}).

	\section*{Multi-Table SQL Queries}
	
	In this part, we validated the logical integration of the database by writing multi-table SQL queries that simultaneously traverse genes, variants, expression data, transcripts, proteins, and structural annotations. These queries were designed directly from the conceptual questions in the project description and test whether the schema supports biologically meaningful questions across data modalities.
	
	\subsection*{Query 4.1: Genes with Variants and Differential Expression}
	
	The first multi-table query asks: \emph{Which schwannoma-associated genes have recorded variants and GEO2R-based differential expression, and how can we prioritize them by both mutational burden and expression change?} To answer this, we joined the \texttt{Genes}, \texttt{variants}, and \texttt{geo2r} tables using Ensembl Gene Stable IDs and HGNC symbols and summarized the number of distinct variants per gene together with log-fold change and adjusted $p$-values from GSE39645. We restricted the output to genes with at least one variant and non-null GEO2R statistics and sorted by decreasing variant count and absolute logFC to highlight potentially important genes.
	
	\begin{sqlcode}
-- Query 4.1: Retrieve genes with their associated variants and GEO2R expression data

SELECT DISTINCT
    g.gene_stable_id,
    g.hgnc_symbol,
    COUNT(DISTINCT v.variant_name) AS variant_count,
    geo.logFC,
    geo.adj_p_value,
    geo.p_value
FROM 
    Genes g
    LEFT JOIN variants v ON g.gene_stable_id = v.gene_stable_id
    LEFT JOIN geo2r geo ON g.hgnc_symbol = geo.gene_symbol
WHERE 
    geo.adj_p_value IS NOT NULL
GROUP BY 
    g.gene_stable_id, g.hgnc_symbol, g.gene_name, geo.logFC, geo.adj_p_value, geo.p_value
HAVING 
    COUNT(DISTINCT v.variant_name) > 0
ORDER BY 
    variant_count DESC, ABS(geo.logFC) DESC
LIMIT 50;
	\end{sqlcode}
	
	This query demonstrates that the database correctly links gene-level identifiers across variation and expression resources, enabling ranking of candidate schwannoma genes based on both mutation load and strength of dysregulation.

	\subsection*{Query 4.2: Proteins, Structural Domains, and Genes}
	
	The second query addresses the question: \emph{For which schwannoma-associated proteins do we have structural domain information from AlphaFold/CATH, and how many domains are annotated per protein?} Here, we joined \texttt{Genes}, \texttt{Proteins}, and \texttt{AlphaFoldCATH} using Ensembl IDs and UniProt/AlphaFold identifiers. For each protein, we counted distinct TED domain identifiers and concatenated their CATH labels. The results are ordered by decreasing domain count and protein length, returning the top 50 structurally rich proteins in the dataset.
	
	\begin{sqlcode}
-- Query 4.2: Find proteins with their structural domains and associated genes

SELECT 
    g.hgnc_symbol,
    p.Entry,
    p.entry_name,
    p.length AS protein_length,
    p.pdb,
    COUNT(DISTINCT ac.ted_id) AS domain_count,
    GROUP_CONCAT(DISTINCT ac.cath_label SEPARATOR '; ') AS cath_labels
FROM 
    Genes g
    INNER JOIN Proteins p ON g.gene_stable_id = p.ensmble_id
    LEFT JOIN AlphaFoldCATH ac ON p.Entry = ac.Alphafold
GROUP BY 
    g.hgnc_symbol, p.Entry, p.entry_name, p.length, p.pdb
HAVING 
    COUNT(DISTINCT ac.ted_id) > 0
ORDER BY 
    domain_count DESC, protein_length DESC
LIMIT 50;
	\end{sqlcode}
	
	This query confirms that structural annotations have been successfully integrated with gene and protein records, allowing downstream analyses that relate domain architecture to disease relevance.

	\subsection*{Query 4.3: Transcripts, Exon Structure, and Expression}
	
	The third multi-table query asks: \emph{Which genes in our schwannoma gene universe have rich transcript structure (multiple RefSeq transcripts and exons) and are also significantly expressed according to GEO2R?} We linked \texttt{Genes}, \texttt{Transcript}, and \texttt{geo2r}, aggregated per gene the number of distinct RefSeq transcripts and summary statistics on exon counts (average, minimum, and maximum), and paired these with logFC and adjusted $p$-values.
	
	\begin{sqlcode}
-- Query 4.3: Retrieve genes with transcript information and expression data

SELECT 
    g.hgnc_symbol,
    g.Chromosome_scaffold,
    COUNT(DISTINCT t.refseq_id) AS transcript_count,
    AVG(t.exonCount) AS avg_exon_count,
    MIN(t.exonCount) AS min_exon_count,
    MAX(t.exonCount) AS max_exon_count,
    geo.logFC,
    geo.adj_p_value
FROM 
    Genes g
    LEFT JOIN Transcript t ON g.hgnc_symbol = t.name2
    LEFT JOIN geo2r geo ON g.hgnc_symbol = geo.gene_symbol
WHERE 
    geo.adj_p_value IS NOT NULL
GROUP BY 
    g.hgnc_symbol, g.Chromosome_scaffold, geo.logFC, geo.adj_p_value
HAVING 
    COUNT(DISTINCT t.refseq_id) > 0
ORDER BY 
    transcript_count DESC, ABS(geo.logFC) DESC
LIMIT 50;
	\end{sqlcode}
	
	This query illustrates how the schema supports exon-aware, transcript-centric views of differentially expressed genes and enables prioritization of genes with complex splicing patterns.

	\section*{Integrated Query for Variations, Proteins, and Expression}
	
	The objective of Part~5 is to write an integrated query that simultaneously retrieves variants, protein-level information, transcript structure, and expression changes for a user-specified gene of interest (for example, \texttt{NF2}, \texttt{DCC}, or \texttt{NBEA}). This tests both the correctness of join paths across all major entities and the usability of the schema for gene-centric exploration. The query below joins \texttt{genes}, \texttt{variants}, \texttt{proteins}, \texttt{Transcript}, and \texttt{geo2r} and filters on a specific HGNC symbol.
	
	\begin{sqlcode}
SELECT 
    g.hgnc_symbol AS gene_symbol,
    v.variant_name,
    p.pdb,
    p.Entry AS uniprot_swissprot_id,
    t.refseq_id,
    t.exonCount AS exon_count,
    geo.logFC
FROM 
    genes g
    LEFT JOIN variants v ON g.gene_stable_id = v.gene_stable_id
    LEFT JOIN proteins p ON g.gene_stable_id = p.ensmble_id
    LEFT JOIN Transcript t ON g.hgnc_symbol = t.name2
    LEFT JOIN geo2r geo ON g.hgnc_symbol = geo.gene_symbol
WHERE 
    g.hgnc_symbol = 'NBEA' -- e.g., DCC , NF2, NBEA
ORDER BY 
    t.exonCount DESC
LIMIT 100;
	\end{sqlcode}
	
	By changing the value of \texttt{g.hgnc\_symbol} in the \texttt{WHERE} clause, we can inspect the full variant catalogue, mapped protein IDs and PDB structures, transcript complexity, and expression logFC for any schwannoma-related gene present in the database.

	\section*{Query for Genes with PDB IDs and Exon Constraints}
	
	The Part~6 question focuses on integrating structural and transcript information: \emph{Which genes have proteins with resolved PDB structures and at least a minimum number of exons in their RefSeq transcripts?} This type of query is useful for selecting candidates suitable for downstream structure-aware analyses, such as modeling exon-specific effects on protein domains. We addressed this by joining \texttt{Genes}, \texttt{proteins}, and \texttt{Transcript}, filtering for non-empty PDB entries and a minimum exon count threshold (here, at least four exons).
	
	\begin{sqlcode}
SELECT DISTINCT
    g.hgnc_symbol,
    g.gene_stable_id,
    p.Entry,
    p.pdb,
    t.refseq_id,
    t.exonCount
FROM 
    Genes g
    INNER JOIN proteins p ON g.gene_stable_id = p.ensmble_id
    INNER JOIN Transcript t ON g.hgnc_symbol = t.name2
WHERE 
    p.pdb IS NOT NULL 
    AND p.pdb != ''
    AND t.exonCount >= 4
ORDER BY 
    t.exonCount DESC, g.hgnc_symbol
LIMIT 100;
	\end{sqlcode}
	
	The result set returns genes for which we have both experimentally resolved or curated structure information and sufficiently complex transcript structures, enabling targeted follow-up analyses.

	\section*{GEO2R Analysis and Downstream Queries}
	
	In Part~7, the goal is to demonstrate how GEO2R-derived differential expression results are integrated into the database and how they can be used to drive downstream queries. Specifically, the questions ask for (i) the number of significantly differentially expressed genes, (ii) the list of these genes, and (iii) how to connect these expression results back to proteins for further analysis. We implemented three SQL queries that operate on the \texttt{geo2r}, \texttt{Genes}, and \texttt{Proteins} tables.

	The first query computes how many genes have an adjusted $p$-value below a significance threshold (here, $0.05$), providing a global summary of the GEO2R analysis.

SELECT

FROM

    adj_p_value < 0.05;

	The third query integrates GEO2R expression results with the \texttt{Genes} and \texttt{Proteins} tables to obtain UniProt entries, protein length, and regulation direction for significantly differentially expressed genes. 	\section*{Challenges Encountered During Physical Design and Loading}
	
	\begin{enumerate}
		\item \textbf{TSV-to-CSV conversion for Workbench import.}
		Some source tables were distributed as TSV. Since our chosen import workflow relied on CSV ingestion through MySQL Workbench, we first converted TSV files into CSV while preserving headers, delimiters, and quoting rules. We validated a small sample after conversion to ensure no column shifts occurred (especially for text fields containing special characters).
		
		\item \textbf{Renaming columns for query-compatibility and consistency.}
		After initial imports, we discovered that several automatically generated column names were inconvenient for downstream SQL (e.g., spaces/special characters, overly long names, or ambiguous names shared across tables). We therefore standardized column naming (consistent snake\_case style) and updated the schema accordingly so that multi-table joins and query writing became straightforward and less error-prone.
		
		\item \textbf{Large file limitation when importing the variants table.}
		The variants dataset was very large (on the order of hundreds of MB). During import, MySQL/Workbench constraints on file size prevented loading the full file in a single step. To proceed, we reduced the dataset to a manageable subset that fits the import constraints (while keeping the schema identical), enabling physical construction, constraint application, and testing queries to run successfully.
		
		\item \textbf{Conceptual vs. practical linkage: GEO2R to Genes.}
		In the Report~1 ERD, we planned to connect \texttt{GEO2R\_Results} to \texttt{Genes} via HGNC gene symbols, which is conceptually reasonable. However, in practice, the available GEO2R outputs and the BioMart-derived gene identifiers did not provide a clean, complete overlap for reliable joining because the tables were produced from different sources/pipelines. This highlighted an important integration lesson: even when two tables share a ``similar'' identifier type in principle, cross-source datasets can differ in coverage and formatting, so link feasibility must be validated empirically early. As a result, we treated this join carefully during constraint definition and testing, and documented the limitation in the physical design discussion.
	\end{enumerate}
